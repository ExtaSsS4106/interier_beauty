# interier_beauty — «Управление записью в салон красоты» (задание №14)

Electron-приложение для ведения клиентской базы, расписания мастеров и учёта
оказанных услуг. Проект собран на существующей архитектура шаблонов (Nunjucks →
`www/templates.js`), роутинга (`www/conf/routing.js`) и IPC-моста
(`electron/preload.js` → `electron/main.js`) — структура проекта не менялась,
добавлены только разделы задания.

## Запуск

```bash
npm install
npm run build      # компиляция шаблонов + сборка www → dist
npm start          # сборка и запуск Electron
```

> Если Electron завершается с ошибкой `The SUID sandbox helper binary ... is not
> configured correctly`, запустите его без песочницы:
> `npm run build && npx electron --no-sandbox .`

При первом старте приложение предлагает подключиться к БД:

* **MySQL / PostgreSQL** — хост, порт, пользователь, пароль (база `interier_beauty`,
  таблицы создаются автоматически через `sequelize.sync()`);
* **SQLite** — локальный файл в папке данных приложения (удобно для отладки и сдачи).

Дальше выполняется первичная регистрация администратора, затем вход по email и паролю.
После входа main-процесс запоминает сессию и **на каждой операции проверяет права
роли** — без входа в систему запросы к БД блокируются.

## Разделение прав (роли)

| Возможность | Администратор | Менеджер | Мастер |
|---|---|---|---|
| Клиенты: просмотр / регистрация | ✔ / ✔ | ✔ / ✔ | ✘ / ✘ |
| Мастера и сотрудники: просмотр | ✔ | ✔ (чтобы направить к мастеру) | ✘ |
| Сотрудники: создание/правка/удаление | ✔ | ✘ | ✘ |
| Услуги: просмотр | ✔ | ✔ | ✘ |
| Услуги: создание/правка/удаление | ✔ | ✘ | ✘ |
| Записи: просмотр | ✔ (все) | ✔ (все) | ✔ (**только свои**) |
| Записи: создание/правка/удаление | ✔ | ✔ | ✘ |
| Статус записи («Принята»/«Оказана»/«Отменена») | ✔ | ✔ | ✔ (только у своих) |
| Отчёты | ✔ | ✔ | ✘ |

Права описаны матрицей в `electron/modules/booking.js` (`ROLE_ACTIONS`, `can()`,
`permissionsFor()`), проверяются **в main-процессе** (`requirePermission()`), а в
UI только прячутся кнопки и пункты меню: у мастера нет фильтра «Мастер», кнопок
«Добавить»/«Редактировать», а попытка открыть `#/clients` сразу возвращает на
главную с уведомлением. Роль `user` из первой версии проекта трактуется как
`manager`.

Статусы записи: `new` (Записана), `accepted` (Принята — мастер принял заказ),
`done` (Оказана), `cancelled` (Отменена).

## Меню — левая выдвижная шторка

Меню перенесено из шапки в левую панель (`templates/sidebar.html`), шапка
(`templates/topbar.html`) осталась только для кнопки-бургера и заголовка раздела.

* кнопка-бургер в шапке и клик по затемнению закрывают панель, `Esc` — тоже;
* состояние (`sidebar-open` на `<html>`) сохраняется в `localStorage` и переживает
  переходы между разделами: на десктопе контент сдвигается вправо, на телефоне
  меню наезжает поверх;
* состав пунктов зависит от прав: мастер видит только «Главная» и «Записи»;
* здесь же карточка пользователя с ролью, ссылка на профиль, выход и переключатель
  темы.

## Отчёт

`#/reports` считает за произвольный период (кнопки «Текущий месяц», «Прошлый
месяц», «Всё время»): количество записей, разбивку по статусам, оказанные услуги,
выручку, план (всё не отменённое) и средний чек, плюс таблицы по услугам,
мастерам и клиентам.

* **Выручка** — только записи со статусом «Оказана»; «Записана» и «Принята»
  попадают в план, «Отменена» не учитывается (об этом написано под фильтрами).
* **Пустой период** больше не выглядит «сломанным»: показывается подсказка с
  диапазоном дат, за которые в базе есть данные (`bounds`), и кнопкой
  «Показать всё время».

## Разделы приложения

| Маршрут | Страница | Что делает |
|---|---|---|
| `#/` | Главная | сводка по базе (клиенты, мастера, услуги, выручка за месяц) и записи на сегодня; состав карточек зависит от роли |
| `#/appointments` | Записи | запись на дату/время, проверка занятости мастера, расчёт стоимости, смена статуса, фильтры по дате/мастеру/статусу, поиск |
| `#/clients` | Клиенты | регистрация клиентов, CRUD, поиск и сортировка |
| `#/masters` | Мастера | регистрация мастеров/сотрудников, CRUD, поиск и фильтр по роли (только админ) |
| `#/services` | Услуги | справочник услуг, CRUD, поиск и фильтр по цене |
| `#/reports` | Отчёты | отчёт за период: количество оказанных услуг, выручка, средний чек, разбивка по услугам/мастерам/клиентам, печать |
| `#/register_db` | Подключение к БД | MySQL / PostgreSQL / SQLite |
| `#/admin_reg`, `#/login` | Регистрация и вход | первичная регистрация и авторизация |

## База данных

Четыре взаимосвязанные таблицы (`electron/modules/db/models.js`, структура не менялась):

```
clients ──< appointments >── employees
services ─┘
```

* `clients` — `first_name`, `last_name`, `number`, `email` (unique);
* `employees` — `first_name`, `last_name`, `email` (unique), `password`, `role`;
* `services` — `title`, `price`, `description`;
* `appointments` — `date`, `time`, `status` (`new` / `accepted` / `done` /
  `cancelled`) + внешние ключи `client_id`, `employee_id`, `service_id`.

## Как это устроено

```
templates/*.html        страницы (Nunjucks) + их inline-скрипты
templates/sidebar.html  левая выдвижная шторка: меню по правам, профиль, выход
templates/topbar.html   шапка раздела: кнопка шторки и заголовок
www/conf/routing.js     маршруты и заголовки
www/conf/render.js      рендер страницы в #root, data.path для активного пункта меню
www/conf/state.js       data.user + permissions (setUser/clearUser)
www/app.js              window.ui — валидация, тосты, подтверждения, форматирование;
                        переключение и сохранение состояния шторки
electron/preload.js     window.db_requests.* → IPC (contextIsolation включён)
electron/main.js        ipcMain.handle: CRUD, записи, отчёты + сессия и права
electron/modules/db/    модели Sequelize + подключения (local/remote)
electron/modules/booking.js   чистая предметная логика (без Electron и БД):
                        валидация, роли/права, статусы, занятость, отчёт
```

Логика вынесена в `booking.js`, поэтому она покрывается обычными node-тестами:
валидация полей, `findConflict()` (занятость мастера), `visitCost()` (стоимость
посещения) и `buildReport()` (количество услуг и выручка).

### Проверка занятости мастера

Перед созданием/изменением записи `main.js` выбирает все записи мастера на эту
дату и вызывает `booking.findConflict()`: слот занят, если есть **не отменённая**
запись с тем же временем. Отменённая запись (`status = 'cancelled'`) слот не
занимает. Ошибка вида «Мастер занят: 25.10.2026 в 14:30 уже записан(а) Иванова
Анна» показывается прямо в форме, а в списке конфликт подсвечивается заранее.

### Расчёт стоимости

Стоимость посещения = цена выбранной услуги: показывается в форме записи,
в таблице записей, в сводке главной страницы и в отчёте.

## Реализация требований ТЗ

1. **Графический интерфейс** — Bootstrap 5, страницы с таблицами, формами и модалками.
2. **Не менее 3 взаимосвязанных таблиц** — 4 таблицы с внешними ключами.
3. **Подключение к БД** — MySQL/PostgreSQL/SQLite через Sequelize, реквизиты
   хранятся в зашифрованном хранилище Electron (`safeStorage`).
4. **CRUD** — добавление, просмотр, редактирование и удаление клиентов, мастеров,
   услуг и записей.
5. **Поиск и фильтрация** — поиск по имени/телефону/email/названию, фильтры по
   роли, цене, дате, мастеру и статусу, сортировка.
6. **Проверка вводимых данных** — валидация на клиенте (подсветка полей) и
   повторная проверка в `main.js` (некорректные данные не доходят до БД).
7. **Обработка ошибок БД** — все IPC-обработчики возвращают
   `{ ok, data | error }`, ошибки Sequelize переводятся на человеческий язык и
   показываются тостом/алертом; удаление записи, на которую ссылаются другие
   данные, блокируется с пояснением.
8. **Отчёт/статистика** — `#/reports` (период, оказанные услуги, выручка,
   средний чек, разбивки) и сводка на главной.
9. **Тестирование** — см. ниже.
10. **Разделение прав** — матрица ролей администратор/менеджер/мастер,
    проверка в main-процессе на каждом обращении к БД, скрытие недоступных
    действий в интерфейсе (см. «Разделение прав»).
